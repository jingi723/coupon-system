Redis 예약 → Relay → Kafka → DB 전체 경로 부하 비교 — 2026-10-14

결론: 두 실행 모두 승인 요청을 중복·누락 없이 최종 발급했다. 예약 응답은 짧지만 폭주 이후 신청도 최종 발급까지 오래 기다린다.
폭주 중에는 Redis pending이 크게 증가하고, 이후 Relay가 전달한 요청이 Kafka에도 쌓인다. 낮은 Kafka lag만으로 전체 적체가 없다고 판단할 수 없다.
서비스 로직/내구성 설정을 개선하거나 변경하지 않았다. 별도 테스트 코드와 관측·분석·문서만 추가했다.

- 코드 기준 f5479a4 + 보존한 테스트 소스. 실행 후 계측 코드는 c081bd5에 커밋. src/main 작업 차이는 없음.

확인한 제한과 아직 분리하지 못한 비용
- 두 실행 모두 1200/s를 Relay가 따라가지 못해 Kafka 이전 Redis pending에 적체됐다. 이후 Kafka에도 적체되어 Consumer 완료가 전달을 따라가지 못하는 구간이 있었다.
- run-1의20–30초 5초 창에서 Kafka 기록 증가 약94–101/s, 이후30–60초 약224–248/s. 상세 회차별 5초 창은 reservation-analysis.json의 throughput_windows.
- 단일Consumer의 DB 연결대기0은 DB 여력이 충분하다는 증거가 아니다. CPU가 낮아도 디스크/왕복/직렬 대기 비용이 있을 수 있다.
- 구간별 Redis 명령/디스크 fsync/Kafka ack/트랜잭션/offset 커밋 시간은 이번에 분리 계측하지 않았다. 낮은 CPU나 AOF delayed_fsync0으로 해당 비용을 배제하지 않는다.
- 완료시간은 HTTP 시작부터 독립 DB 조회가 커밋된 결과를 관측할 때까지다. 조회는 목표250ms이며 실제 간격과 누락0을 검증했다. 정확한 커밋시각/큐 대기시간 자체는 아니다.
- DB 건수/s는 관측 시점으로 묶은 수치다. 초별 CSV와 5초 창을 함께 본다. 짧은 창에는 관측 경계 오차가 포함된다.
- pending/processing/lag는 순차 조회이고 전달 중 레코드는 겹칠 수 있다. 최대치를 합산해 전체 적체나 시간비율을 계산하지 않았다.
- 상세 요청 로그를 서비스에 추가하지 않았다. 하지만 관측 쿼리·k6 원시 기록·docker stats의 오버헤드는 남으며, 관측 비활성 대조 실행은 이번에 하지 않았다.
- CPU/쓰기 값은 관측 시작부터 최종 안정화까지 포함한다. 데이터/로그 쓰기 누적 바이트는 fsync 횟수나 디스크 지연을 의미하지 않는다.
- run-1 종료 정리 단계에서 LettuceConnectionFactory STOPPING 오류가 기록됐다(application.log 374행). 전량 처리·안정화·최종 스냅샷 이후 graceful shutdown 중 발생했으며 부하 중 처리 실패와 구분한다. 종료 순서 검토 사항으로 남기고 서비스 수정은 하지 않았다.

추천하는 다음 실험 하나
AOF always를 유지하고 Relay 한 건의 처리시간을 processing 조회/LMOVE/예약 조회/Kafka ack 대기/LREM 반환으로 나눠 테스트 전용 단조시계 집계한다.
계측 비활성/활성 대조와 같은 부하의 반복 실행을 포함한다. 이번 폭주에서 먼저 늘어난 pending의 원인이 Redis 왕복·fsync인지 Kafka ack 대기인지 확인한 뒤 개선안을 선택한다.
트랜잭션1건/10건 비교는 Consumer 측 비용 확인을 위한 후속 후보로 유지하지만, Redis 전달 적체의 원인을 확인하지 않고 전체 병목이 해결된다고 가정하지 않는다.
