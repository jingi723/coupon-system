동기 발급 재측정 — 2026-10-01 (Asia/Seoul)

대상: main / 870c575c0d854545ad71e430ec3615dddf3b0de2, 서비스 코드 변경 없음.
Redis Lua 판정 → DB 조건부 원자적 UPDATE → 발급 이력 INSERT 및 flush → 성공 응답.
직전 실험과 같은 arrival.js를 사용. 이전 실험은 미커밋 상태였으므로 결과를 구분한다.

환경과 조건:
로컬 앱·MySQL·Redis·k6. MySQL CPU 1개/메모리 1GiB, Redis CPU 0.5개/256MiB.
Java 17, ./gradlew bootRun --args='--spring.jpa.show-sql=false'.
각 실행 새 쿠폰/재고 100000/고유 사용자. 재고 소진·중복 거절 없음.
constant-arrival-rate, 30초, preAllocatedVUs=600, maxVUs=1500.
클라이언트 timeout=60초, gracefulStop=65초. 각 부하를 순서대로 1회씩, 별도 워밍업 없음.
기존 데이터는 유지. 오류 로그를 제외한 SQL 출력은 끔.

전 단계 네트워크 오류·기타 응답 0건. 서버 SQL 오류·데드락 로그 0건.
각 실행의 예정 iteration이 경계 시점에 1회 추가되어 9001/21001/36001회로 집계됨.
미전송은 k6 dropped_iterations. 서버에 도달한 실패 요청이 아니므로 5xx와 구분.
700/1200 모두 Insufficient VUs 경고 발생: 지연으로 최대 1500 VU가 모두 점유됨.
실제 발급 요청 수/30초는 각각 약 300.0/498.8/493.6건/초.
지연 통계는 발급 HTTP 요청만 포함. 쿠폰 생성과 Redis 초기화 요청은 제외.
성공 건수는 유입을 중단한 뒤 gracefulStop 중 완료한 요청까지 포함하며,
성공 건수/30초를 DB의 정상 상태 처리량이라고 해석하면 안 됨.

DB 처리량과 대기:
300: 실행 약 12.40~28.27초 구간, 4763건 증가 / 15.87초 ≈ 300.1건/초.
700: 실행 약 12.41~28.25초 구간, 7128건 증가 / 15.83초 ≈ 450.2건/초.
1200: 실행 약 12.43~28.18초 구간, 6651건 증가 / 15.75초 ≈ 422.4건/초.
위 값은 주기적 DB 발급 이력 COUNT의 차분 추정치. 조회와 모니터링 비용도 포함됨.
700/1200 실행 중 각각 한 번 얻은 스레드 덤프에서 HTTP 요청 스레드 190개가
HikariPool.getConnection / ConcurrentBag.borrow에서 연결을 기다리고 있었음.
300 단계 단일 덤프에서는 해당 대기 스레드 0개.
DB Innodb_row_lock_current_waits의 관측 최대는 각각 0/9/9.
DB 진단과 연결 대기를 함께 보면 동일 쿠폰 행 UPDATE의 락 대기가 처리량을 제한하는 근거가 있음.
단일 스레드 덤프나 3초 주기 샘플은 실행 전체의 최대값이나 지속 상태를 보장하지 않음.

해석:
이번 버전/실행에서는 데드락 및 수량 불일치가 재현되지 않았다.
목표 부하를 올리자 DB 연결·행 락 대기와 응답 지연이 증가했다.
다만 k6가 VU 상한에 도달해 목표 700/1200건/초를 30초 내내 전달하지 못했다.
따라서 이 결과는 실제로 1200건/초를 계속 수용했다거나 그 조건에서도 타임아웃이 없다는 증거가 아니다.
이번 관측 범위의 성공 경로 저장 속도는 높은 부하에서 약 420~450건/초였다.
최대 처리량의 정밀 추정, 장시간 과부하 시 오류 시점, Kafka 효과는 이 실험으로 확정하지 않는다.
기존 2026-08-17의 663 RPS와는 실행 방식·환경 상태가 달라 성능 회귀를 단정할 수 없다.
