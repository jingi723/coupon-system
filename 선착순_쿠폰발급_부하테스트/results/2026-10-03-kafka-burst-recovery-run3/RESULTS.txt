Kafka 순간 폭주 비교 — 2026-10-03

핵심: 접수 응답은 빨라졌지만, 현재 단일 Consumer의 최종 발급 완료는 기존 동기 방식보다 늦었다.
모든 신청은 최종 발급됐으며 중복·미완료는 없었다. 대기는 DB 연결 풀 대신 Kafka lag로 관측됐다.

비교 대상과 측정 정의
기존: results/2026-10-01-burst-recovery, d34f76c의 Redis 판정 → 동기 DB 저장 → 200.
현재: a032e97 + 사용자 미커밋 Kafka 경로(working-tree.patch에 보존), Kafka 기록 확인 → 202 → Consumer DB 처리.
현재 경로는 Redis 선차감 없이 DB에서 판단하며, 발급 이력 외에 요청별 처리 결과도 저장한다.
파티션 1, Consumer 1, RECORD offset 커밋. 따라서 Kafka 유무만 바뀐 통제 실험은 아니다.
앱은 새 JVM/18080, 테스트 Kafka 3.7.0은 별도 29092. 기존 앱/브로커는 유휴 상태로 유지했다.
MySQL 8.0 CPU 1개/1GiB, Kafka CPU 1개/1GiB, Hikari 풀 10. 같은 호스트에 다른 서비스도 실행 중이다.
접수 지연 = HTTP 호출 직전부터 202 응답까지. 최종 지연 = 같은 전송 시각부터 독립 JDBC 조회로 커밋된 결과를 처음 확인하기까지.
processed_at은 커밋 완료 시각이 아니므로 완료시간 계산에 사용하지 않았다.
DB 조회 간격 목표 250ms, 실제 min/p95/max = 250/255.0/353ms.
최종 지연에는 DB 조회 대기가 포함된다. 특히 평상시 약 250ms p95를 실제 DB 처리시간으로 해석하면 안 된다.
JMX 풀 대기 약 250ms, Kafka offset 약 250ms, DB 행 락 약 1초 관측. 샘플 사이의 짧은 대기는 놓칠 수 있다.
Kafka lag는 커밋 위치와 end offset의 순차 조회 차이다. 동시 원자 스냅샷이 아니며 DB 미완료 건수와 정확히 같지 않다.

목표: 100/s 20초 → 1200/s 3초 → 100/s 30초. VU 50/3600/1000, 재시도 없음, timeout 60초.
명목 8600건. 시나리오별 실제 전송: baseline 2016, burst 3600, recovery 3001 = 8617건.
모든 시나리오 dropped_iterations=0. 실제 API 202=8617, 명시적 거절/5xx/응답 불명/타임아웃=0.
부하 발생기 시각 편차: baseline 전송 0~20.155초, burst 20.191~23.155초, recovery 23.008~53.000초.
burst 시나리오의 시작 기준은 공통 원점 대비 목표보다 155ms 늦었다. recovery는 1ms 빨랐다.
따라서 정확히 [20,23)초에 전송한 요청은 3433건이다. 폭주 시나리오 3600건을 모두 이 구간에 보냈다고 해석하면 안 된다.
전체 전송 시각 구분: [0,20) 1996건 / [20,23) 3433건 / [23,53) 3187건 / 53초 경계 1건.
아래 구간은 기존 분석과 같은 공통 원점의 예정 경계(23초)를 기준으로 한다. 실제 폭주 마지막 전송은 155ms 뒤였다.
이 편차 때문에 정확히 같은 순간 유입 곡선이라고 단정할 수 없으며, 성능 수치의 엄밀한 배율 비교에는 제한이 있다.

3. 적체와 회복
관측 최대 lag=3214, 공통 원점 23.179초에 관측. 풀 연결 대기·행 락 대기는 전체 샘플에서 0.
기존 동기 실험의 회복 첫 5초 최대 풀 대기는 190, 행 락 대기는 8이었다.
폭주 구간 [20,23)에 전송한 요청의 마지막 결과 확인: 예정 폭주 종료 후 12.543초. 기존 동기 마지막 폭주 응답은 2.558초.
폭주 종료 후 최초 lag=0 관측: +21.630초. 이후 평상시 유입으로 작은 lag가 다시 나타날 수 있다.
관측 종료까지 lag=0이 유지되는 샘플 시작: +29.698초. 이는 최초 적체 해소 시각과 다른 지표다.
마지막 요청 전송 53.000초, 마지막 결과 확인 53.197초. 모두 처리된 후 추가 10초 이상 관찰했다.
사전 회복 기준: 평상시 5~10/10~15/15~20초 p95 최댓값의 2배 이내 + 풀 대기 샘플 0이 두 5초 구간 연속 유지.
접수 기준 상한 6ms: 0~5초와 5~10초 구간이 충족하여 예정 폭주 종료 +10초에 확인.
최종 확인 기준 상한 568.5ms: 마지막 25~30초 구간만 충족. 두 구간 연속 조건은 실험 범위에서 확인하지 못했다.
기존 동기 기준 충족은 +15초. 새 기준의 수치가 다르고 완료 관측 방식도 달라 단순 동등한 SLO 비교는 아니다.
최종 lag=0과 모든 발급 완료를 확인했으나, 이것만으로 새 요청 지연의 연속 두 구간 회복을 대신 판정하지 않았다.

4. 최종 정합성
쿠폰 ID 18, 재고 100000. 202 접수 8617 = DB 결과 ISSUED 8617 = 발급 이력 8617 = issued_quantity 8617.
고유 발급 사용자 8617. REJECTED 0, 중복 0, 접수 후 미완료 0, 접수에 없는 결과 0, 최종 lag 0.
접수 requestId→userId 전체 맵과 DB 결과 맵이 일치한다. 결과의 issuedCouponId→userId 맵도 발급 이력 전체와 일치한다.
이번 Kafka 경로는 Redis 재고를 사용하지 않는다. 남은 발급 가능 수량은 DB 기준 91383이다.

5. 해석과 제한
이번 구성에서는 접수 지연을 낮추고 요청을 보관하는 효과를 확인했다. 발급 처리 자체가 빨라졌다는 결과는 아니다.
단일 Consumer의 순차 처리, 추가 결과 저장, RECORD 커밋 등이 기존 동기 경로와 다르다.
어느 요소가 얼마나 영향을 주었는지는 분리 측정하지 않았으므로 느린 원인을 Kafka 자체로 단정하지 않는다.
단일 유효 실행이며 캐시/호스트 경쟁/실행 시각 차이가 있다. 처리량 최대치나 운영 환경의 일반 성능을 의미하지 않는다.
첫 준비 실행(상위 2026-10-03-kafka-burst-recovery)은 관측 도구 설정 오류로 부하 전 종료했다.
run2는 8603건 정합성은 통과했으나, 마지막 처리 중 호스트 시계가 약 1866ms 뒤로 이동하여 시간 비교에서 제외했다.
run3는 wall clock과 monotonic 간 250ms 샘플 차이를 검사했고, 최대 오차 0.967ms였다.
raw 로그/원본 결과는 각 폴더에 보존한다. 본 보고서는 run3만 공식 비교값으로 사용한다.

재현
