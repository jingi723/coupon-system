모든 요청을 baseline의 공통 시각 원점으로 다시 정렬했다.
각 시나리오가 보고한 시작 시각에 1ms 차이가 있어, 원본 phase 태그 대신
절대 sent_ms를 기준으로 분석했다. 완료 시각에 의한 재분류는 하지 않았다.

환경 및 한계
앱·k6·Docker DB·Redis는 같은 macOS 호스트에 있다. 상세 환경은 environment.json.
MySQL CPU 1개/메모리 1GiB, Redis CPU 0.5개/256MiB.
앱은 --spring.jpa.show-sql=false --spring.datasource.hikari.register-mbeans=true 로 실행.
Hikari 풀은 10개 연결. JMX는 로컬 Attach API로 읽었으며 서비스 파일 변경은 없다.
0.25초 JMX와 1초 DB 조회, k6 JSON 출력 비용도 이번 결과에 포함된다.
단일 실행 결과이며 다른 폭주 지속시간이나 운영 환경의 성능을 일반화하지 않는다.
Kafka 적용 후 같은 프로필과 전송 시각 기준으로 비교하되, 접수와 최종 발급 완료를 분리해야 한다.
이번 실행에서는 3초 폭주만으로 적체와 후속 요청 지연이 확인되어 폭주 시간을 늘리지 않았다.

파일 및 재현
k6-burst-recovery.js: 프로필과 요청별 전송 시각/결과 기록.
PoolSampler.java: Hikari JMX를 0.25초마다 기록.
run-burst-recovery.py: k6와 DB/JMX 관측 실행. 출력 폴더는 비어 있어야 함.
analyze-burst-recovery.py: 전송 시각별 분석, DB/Redis 사용자 ID 대조.
analysis.json / requests.csv: 최종 분석과 요청별 기록.
metrics.json.gz / pool.csv / db-samples.jsonl: 원시 측정 자료.
분석기는 DB와 Redis가 켜져 있을 때 실행한다. 테스트 폴더 상위의 원본 스크립트와
이번 실행에 사용한 사본을 이 결과 폴더에 함께 보관했다.

프로젝트 루트에서:
docker compose up -d mysql redis
./gradlew bootRun --args='--spring.jpa.show-sql=false --spring.datasource.hikari.register-mbeans=true'
python3 선착순_쿠폰발급_부하테스트/run-burst-recovery.py APP_PID EMPTY_OUTPUT_DIRECTORY
python3 선착순_쿠폰발급_부하테스트/analyze-burst-recovery.py EMPTY_OUTPUT_DIRECTORY
