Kafka 장애 복구 테스트 — 2026-10-02

결과: 장애 복구 시나리오 3개 통과. 기존 테스트를 포함한 전체 52개 통과.
실제 Kafka 3.7.0, MySQL 8.0 Testcontainers와 별도 애플리케이션 JVM을 사용했다.
기존 로컬 Kafka/DB/Redis 및 실행 중인 API에는 장애를 주입하지 않았다.

1. API 유지 + Consumer 정지/재개
재고 2개 쿠폰에 Consumer를 완전히 정지한 뒤 신청 3건을 POST했다.
3건 모두 HTTP 202/ACCEPTED. 앱 프로세스와 API는 계속 살아 있었다.
정지 중 Kafka lag=3, DB 발급 수량=0, 발급 이력=0, 처리 결과=0.
Consumer를 재개하자 ISSUED 2건, REJECTED 1건으로 모든 requestId가 최종 결과와 대응했다.
최종 수량=2, 발급 이력=2, 처리 결과=3, lag=0.

2. DB 커밋 후 offset 커밋 전 강제 종료
별도 서비스의 실제 DB 트랜잭션이 끝난 뒤 Consumer가 Kafka 컨테이너에 반환하기 전에
테스트 전용 프록시로 Listener 스레드를 대기시켰다.
중단 지점 표식 transactionActive=false 및 별도 JDBC 연결로 조회한 DB 상태를 함께 검증했다.
DB에는 수량=1, 발급 이력=1, 처리 결과=1이 이미 커밋되어 있었다.
해당 레코드는 topic=coupon-issue-requests, partition=0, offset=3.
그룹의 커밋된 다음 읽기 위치는 여전히 3, 토픽 끝 위치는 4였다.
이 상태에서 Process.destroyForcibly()로 앱 JVM을 강제 종료하고 비정상 종료를 확인했다.
같은 Consumer 그룹으로 새 JVM을 시작했다. API 재접수나 Producer 재발행은 하지 않았다.
재시작 후 최초 전달과 동일한 topic/partition/offset/requestId가 다시 관측됐다.
DB 수량/발급 이력/처리 결과는 모두 1을 유지했고, 발급 이력 ID와 처리 결과 ID도 동일했다.
토픽 끝 위치는 4로 유지되어 새 메시지가 추가되지 않았고, 커밋 위치만 3→4로 전진했다.
정확한 그룹명, 요청 ID, PID 및 DB ID는 summary.json 참조.

3. 실제 DB 오류에 따른 Consumer 중단과 수동 재개
테스트 DB의 결과 테이블에 특정 requestId INSERT를 거절하는 CHECK 제약을 추가했다.
API는 해당 신청을 202로 접수했지만 Consumer의 DB 저장은 실제로 실패했다.
수량/발급 이력/처리 결과는 전부 롤백되어 0이었다.
CommonContainerStoppingErrorHandler에 의해 Listener가 중단됐음을 확인했다.
이 상태에서도 후속 신청은 API에서 202를 받았고, Kafka에 함께 대기했다.
제약을 제거해도 Listener는 중단 상태를 유지했다. 자동 재시도가 아님을 확인했다.
명시적으로 재개하자 실패했던 offset 4가 재전달되고, 이어서 offset 5가 처리됐다.
전달 순서: 4(실패) → 4(재처리 성공) → 5(후속 성공).
최종 수량=2, 발급 이력=2, 결과=2, lag=0.

구현과 실행
src/test/.../issuerequest/recovery/KafkaRecoveryTest.java: 시나리오와 DB/offset 검증.
src/test/.../issuerequest/recovery/RecoveryTestApplication.java: 별도 JVM 진입점과 테스트 전용 제어/중단 장치.
제어 엔드포인트는 테스트 클래스패스 + recovery-probe 프로필에서만 제공한다.
운영 소스에는 제어 API나 장애 주입 코드를 추가하지 않았다.
각 테스트의 부모 JVM이 실제 앱 프로세스를 시작/종료하고, 외부 JDBC 및 Kafka Admin으로 관측했다.
테스트 종료 시 전용 자식 앱과 컨테이너를 정리했다.

Docker 실행 후 프로젝트 루트에서:
./gradlew test --tests '*KafkaRecoveryTest'
전체 검증: ./gradlew test
실행별 진단: build/recovery-evidence/<실행별 UUID>/
최종 통과 실행의 증거를 현재 결과 폴더에 복사해 보존했다.

한계와 다음 비교
이번 검증은 레코드 재전달의 안전성과 보관/재개 기능 검증이다.
브로커 디스크 손실, 복제본 장애, 여러 파티션/Consumer 동시 처리, 장시간 장애는 검증하지 않았다.
Kafka의 보관 기간 내 재개하는 조건이다. 강제 종료 경계는 테스트 장치로 의도적으로 고정했다.
폭주 성능 비교는 아직 실행하지 않았다. 기존 프로필로 API 접수 지연과 최종 DB 발급 지연을
분리하고, 실제 전송량/lag/회복 시간을 함께 비교하는 단계가 다음이다.
