# k6 부하 실측 결과 (2026-08-17)

`k6-load-test.js`로 측정. 환경: 로컬 macOS 단일 호스트(앱·MySQL·Redis·k6 동일 머신),
docker compose MySQL(13306)·Redis, Spring Boot 8080, `--spring.jpa.show-sql=false`.

## 비교 대상

- Before — pre-Redis HTTP 경로 (커밋 `14f95c6`): 조건부 atomic UPDATE + (coupon_id, user_id) unique constraint
- After — 현재 main (`1071dac`): Redis Lua 원자 판정(SISMEMBER+재고 확인+DECR+SADD) → DB 저장, 실패 시 Redis rollback

부하 형태: constant-vus 300, 30초, 요청마다 전 실행에서 고유한 userId.
시나리오당 새 쿠폰 생성 후 `stock/init`으로 초기화.

## 결과

| 300 VUs · 30초 | Before (atomic UPDATE) | After (Redis Lua) |
|---|---|---|
| 선착순 재고 100 — 처리량 | 3,325 RPS | 5,112 RPS (+54%) |
| 선착순 재고 100 — p50 / p95 | 88.4ms / 102.1ms | 55.8ms / 94.3ms |
| 선착순 재고 100 — 발급 수 | 100 (DB 저장 100) | 100 (DB 저장 100) |
| 재고 소진 후 거절의 행선지 | 100,157건 전부 MySQL 도달 (요청당 UPDATE 1회) | 154,378건 Redis에서 흡수, DB 도달 0건 |
| 재고 충분 100,000 — 처리량 | 674 RPS · p50 444ms | 663 RPS · p50 450ms |
| 5xx | 0건 | 0건 |

## 해석

- 선착순의 실제 부하는 재고 소진 후의 거절 폭풍이다. Before는 거절도 전부 DB 트랜잭션으로
  처리하지만, After는 Redis Lua 판정이 DB 앞에서 흡수해 소진 후 DB 부하가 0이 된다.
- 재고가 남아 있는 구간에서는 두 버전이 사실상 동일하다. 발급 성공 경로는 양쪽 모두
  coupon row에 대한 DB 쓰기(atomic UPDATE + insert)가 지배하며, HikariCP 기본 풀(10) 기준
  약 660~670 RPS에서 수렴한다. Redis 도입의 이득은 이 구간이 아니라 거절 구간에 있다.
- 모든 실행에서 발급 수 = DB 저장 수 = 재고. 총 45만여 요청에서 5xx 0건.

## 한계

- 단일 호스트 실측이라 네트워크 지연이 없는 조건이다.
- 비관적 락 버전은 HTTP 경로에 연결된 적이 없어(JUnit 동시성 테스트에서만 사용)
  HTTP 부하 비교 대상은 atomic UPDATE 버전이다.
- 재고 충분 구간의 처리량은 커넥션 풀 크기 설정에 의존한다.

## 재현

```bash
docker compose up -d
./gradlew bootRun --args='--spring.jpa.show-sql=false'

# After (main)
k6 run -e RUN_SEED=1 -e VUS=300 -e DURATION=30s -e STOCK=100 선착순_쿠폰발급_부하테스트/k6-load-test.js

# Before
git checkout 14f95c6   # 측정 후 git checkout main
```

RUN_SEED는 실행마다 다른 값을 주어야 userId가 이전 실행과 겹치지 않는다.
