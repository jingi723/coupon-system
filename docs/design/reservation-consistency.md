# Redis 예약 정합성 설계

현재 첫 버전은 행사 전 수량/기간 고정, 진행 중 증량·취소 미지원, 승인된 예약의 행사 종료 후 발급, 장애 시 예약 유지·재처리, 단일 Relay입니다. 아래 검토안의 미확정 정책과 구분합니다.

### Redis를 발급 판정 기준으로 두는 구조 — 사용자 의도와 조사, 2026-10-03

사용자는 처음 생각한 구조가 Redis에서 발급 시점의 재고·대상을 결정하고 큐로 DB에 전달하는 방식이었다고 설명했다. 현재 구현은 Redis를 거치지 않는 Kafka 접수→DB 판정이며, 두 구조는 다르다. 조사 후 사용자가 이 방향을 Kubernetes보다 먼저 진행하기로 선택했다. 직접 구현하는 실습 원칙은 유지하며, 에이전트의 코드 작성·실행 승인이나 구현 완료를 의미하지 않는다. Redis 없이 시작한 안은 연결·복구를 단순화하는 첫 단계 제안이었으며 사용자 의도 전체를 대체하는 확정 설계로 취급하지 않는다.

- [올리브영 선착순 쿠폰 정합성 개선](https://oliveyoung.tech/2025-12-15/fcfs-coupon/) — 2025-12-15 기업 운영 사례, 2026-10-03 본문 확인. Redis에서 수량을 조회해 통과시킨 후 Worker가 수량을 반영하던 시간 간극과 GET/INCR 경합을 설명한다. 앞단 수량 선차감과 이중 카운터를 조합했다. Redis 수량 관리→MQ→DB 비동기 반영의 실무 근거이며 Redis가 모든 장애에서 유일한 영속 정본임을 입증하는 자료는 아니다. 해당 글의 성능 비교와 실패 보상 방식을 다른 구현에 그대로 일반화하지 않는다.
- [Redis Lua 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/) — 2026-10-03 확인. Redis 안의 재고 검사·사용자 중복 판정·예약 기록을 한 실행으로 묶는 설계가 가능하다. 이 실행의 원자성이 Kafka 쓰기나 DB 트랜잭션까지 확장되는 것은 아니다.
- [Redis 영속화](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [복제](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) — 2026-10-03 확인. 메모리에서 판정한 결과를 장애 후 복원하는 문제는 별도다. 영속화 정책별 손실 가능성과 비동기 복제의 한계를 고려해야 하며 WAIT도 모든 장애에서 확인된 쓰기를 보장하는 강한 일관성 시스템으로 바꾸지 않는다.
- [Kafka 전달 의미](https://kafka.apache.org/41/design/design/#semantics) — 2026-10-03 확인. 전송 결과가 불명확하거나 DB 처리 후 offset 커밋 전에 중단되는 경우를 고려해야 한다. Kafka의 멱등 Producer·트랜잭션이 Redis 변경을 함께 커밋하는 것은 아니다.

**설계 해석:** Redis는 행사 중 남은 재고와 배정된 사용자·요청의 판정 기준, Kafka는 배정 결과 전달 기록, DB는 반영된 발급·사용 이력의 영속 저장소로 역할을 나눌 수 있다. 이때 DB는 지연될 수 있으므로 미반영 예약을 제외한 DB 수량만으로 Redis를 재초기화하면 안 된다. 영구적인 복구 기준으로 무엇을 보존할지는 별도로 명시해야 한다.

**현재 경로와 달라지는 점:** 현재 Kafka에는 아직 재고가 확보되지 않은 신청이 들어간다. 검토안에서는 재고를 확보한 예약/배정 결과가 들어가며, Consumer의 주 역할은 그 결정을 멱등하게 DB에 반영하는 것이다. 이미 배정된 요청에 현재 시각·잔량으로 다시 추첨하듯 발급 여부를 결정하지 않도록 정책을 맞춘다. DB 유일성 제약과 안전장치·불일치 감지는 유지한다.

**구현 전에 정할 경계:** (1) Redis 예약 후 Kafka 발행 전 앱 종료 시 미전송 예약 복구, (2) Kafka 전송 타임아웃에 무조건 재고를 되돌려 중복 배정하지 않기, (3) DB 장애 시 예약을 유지하며 재시도할지 취소할지 결정, (4) Redis 데이터 손실 시 미반영 예약까지 복원한 뒤 접수 재개, (5) 사용자 응답의 신청 접수·예약 확정·사용 가능한 발급 완료 구분. 요청 ID와 예약 상태, 재전송 가능한 기록 및 대사가 필요하다.

**사용자 선택에 따른 다음 진행 순서:**

1. 예약의 의미와 성공 응답 시점, Redis·Kafka·DB의 역할, 재시도·취소 상태를 설계한다. 예약 기록과 미전송 복구 기록을 어떻게 함께 남길지 먼저 정한다.
2. 사용자가 Redis의 재고·중복 판정·예약 기록을 구현한다. 같은 requestId 재요청이 새 예약을 만들지 않고 기존 상태를 반환하는지 확인한다.
3. 예약을 Kafka로 전달하고 Consumer가 DB에 멱등하게 반영하도록 연결한다. DB 유일성 제약·트랜잭션은 유지하며 기존 DB 재고 판정 로직과의 역할 충돌을 검토한다.
4. 예약 직후 앱 종료, 전송 결과 불명, 메시지 중복, DB 실패 및 Redis 복구에서 정합성을 검증한다. 이후 동일 폭주 조건으로 접수·예약 응답과 최종 DB 반영 지연을 비교한다.

기존 동기 및 Kafka→DB 판정 버전과 측정 결과는 비교 기준으로 보존한다. Consumer 성능 계측은 필요에 따라 활용하되, 지금의 선행 작업은 예약·전달의 신뢰성 설계다. Kubernetes와 배포 확장 실습은 이 단계 이후로 둔다.


### 쿠폰 비동기 도입 근거 조사 — 2026-10-03

사용자 요청으로 실제 쿠폰 운영 사례와 공식 설계 문서 본문을 확인했다. 학습용 구현 사례는 운영 근거로 사용하지 않았다. 아래는 외부 사실과 프로젝트 적용 판단을 구분한 기록이다.

- [올리브영 쿠폰 발급 개선 이야기](https://oliveyoung.tech/2022-09-28/Oliveyoung-Coupon-Count-Moving-Redis/) — 2022-09-28, 기업 운영 사례. 행사 중 발급 수량 확인의 DB 경합을 설명하고 Redis 조회로 개선했다. 큐 도입 이전의 DB 부하 개선 사례다.
- [올리브영 비동기 쿠폰 발급](https://oliveyoung.tech/2023-08-07/async-process-of-coupon-issuance-using-redis/) — 2023-08-07, 기업 운영 사례. 동기 발급의 DB 연결 점유·긴 대기를 이유로 발급 Worker를 분리했다. 전환 중 스트레스 테스트에서 Pub/Sub 다중 구독의 과발급과 전달 문제의 미발급을 발견해 별도 보완했다. 여기의 유실은 동기 처리 과부하에서 발생한 사례가 아니다.
- [올리브영 RabbitMQ 도입](https://oliveyoung.tech/2023-09-18/oliveyoung-coupon-rabbit/) — 2023-09-18, 위 시스템의 후속 운영 개선. 안정성과 확장 요구로 RabbitMQ를 선택하고 prefetch·concurrency를 구성했다. 비동기 필요성과 Kafka 선택은 별도 판단이다.
- [AWS: Using load shedding to avoid overload](https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload) — Amazon의 과부하 설계 설명. 타임아웃 뒤 재시도가 부하를 증폭시키고 서버 완료와 클라이언트 실패가 공존할 수 있음을 설명한다. 본 프로젝트의 재시도 폭증은 아직 측정하지 않았다.
- [AWS: Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) — 결과 불명확과 중복 실행을 다루는 공식 설계 설명. 요청 식별과 멱등성은 동기·비동기 모두에 필요한 대책이다.
- [Azure: Queue-Based Load Leveling](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling) — 공식 설계 패턴, 문서 갱신 2026-06-12. 접수와 소비 속도를 분리하고 Consumer의 하위 시스템 호출량을 제어한다. 큐의 내구성, 멱등성, 적체와 순서 보장은 별도 고려사항이다.
- [Azure: Asynchronous Request-Reply](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply) — 공식 API 설계 패턴. 202 접수와 상태 조회를 나누고, 응답 유실 시 멱등 재시도를 지원하는 방식이다. 202만 반환하면 사용자에게 최종 결과를 제공하는 기능이 완성된 것은 아니다.

**적용 판단:** 유실 발생을 비동기 도입의 필수 선행 조건으로 삼지 않는다. 이번 실습의 목적은 순간 유입을 보관하고 DB 처리 속도와 분리하며, 접수 여부와 최종 결과를 추적하는 것이다. DB 트랜잭션·재고 조건부 갱신·중복 방지는 정합성 장치이며 비동기 전환만으로 대체되지 않는다. 최신 사용자 보고의 동기 타임아웃과 전량 발급은 모순이 아니며, 동기 과부하 유실로 재해석하지 않는다. 이후 처리 속도 개선은 요구하는 완료시간을 맞추기 위한 별도 과제다.

여기어때의 Redis/Kafka 네고왕 글은 원문 접근 시 본문을 확보하지 못해 이번 판단 근거에서 제외했다. 모든 출처 확인일은 2026-10-03이다.

### Redis 예약→Kafka→DB 정합성 계약 — 2026-10-04 설계 검토

> 2026-10-05 사용자 범위 확정으로 아래의 증량·취소·다중 노드 설계는 후속 참고 사항이다. 첫 버전의 구현 범위와 순서는 문서 끝 「첫 버전 확정 범위」를 우선한다.

이번 요청 범위는 현재 코드·문서·Redis 런타임 설정의 읽기와 README 정리다. 코드·설정 변경, 테스트 실행, 커밋은 하지 않았다. 검토 기준 HEAD는 `1eeaaee`이고 로컬 문서·성능 실험 자료는 별도 미커밋 상태다. 앞의 실험 기록은 당시 구조의 결과로 보존하며, 아래 계약이 최신 구현 순서의 기준이다.

#### 확정 방향과 미확정 정책

**사용자 확정 방향:** Redis에서 재고·중복을 판정하고 재고 차감·예약 저장·pending 등록까지 성공하면 예약 결과를 응답한다. Kafka 전달과 DB 반영은 이후 비동기다. Kafka ack나 DB 커밋을 예약 응답의 선행 조건으로 바꾸지 않는다. 예약 확정과 사용 가능한 발급 완료는 별개다.

**아직 제안인 부분:** 예약 응답의 HTTP 상태·표시명, 장애 범위/RPO(허용 유실량)/복구시간, Redis 영속성 확인 방식, 예약 시점의 행사 정책 고정, 관리자 중지의 효력 시점, 취소 허용 범위·재신청 여부·쿠폰 사용 만료일 기준이다. 아래 권장안을 사용자 승인 또는 구현 완료로 기록하지 않는다. 특히 “Redis 명령 성공만 확인한 즉시 응답”과 “장애에도 확정 예약 유실 없음”을 현재 설정에서 동시에 보장할 수 없다.

권장 시작안은 예약 성공 응답을 `202 + requestId + RESERVED`로 표현하고, 화면에는 “예약 확정·발급 처리 중”을 표시하는 것이다. 사용은 DB의 ISSUED 이력 커밋 이후에 허용한다. Redis 예약 쓰기의 내구성 확인이 필요하면 그 확인까지를 Redis 예약 성공 경계로 정의한다. 이 확인 역시 Kafka/DB 완료 대기와는 다르다.

#### 1. 데이터별 판단 기준

**현재 구현**

- [CouponService](../../src/main/java/com/assignment/coupon_system/coupon/service/CouponService.java)와 [Coupon](../../src/main/java/com/assignment/coupon_system/coupon/entity/Coupon.java): DB `totalQuantity`, `issuedQuantity`, ACTIVE 상태, 발급 기간을 보유한다. 관리자 증량 명령·변경 이력·전달 기록은 없다.
- [CouponIssueRedisService](../../src/main/java/com/assignment/coupon_system/coupon/redis/CouponIssueRedisService.java): Lua에서 stock 차감, 사용자 Set, requestId별 Hash, pending을 함께 기록한다. Hash에는 requestId/couponId/userId/reservedAt만 있고, 영구 예약 상태·정책 버전·취소·증량 적용 기록은 없다. `CouponReservationStatus`는 호출 결과 enum이며 Hash에 저장된 생애주기 상태가 아니다.
- [신청 API](../../src/main/java/com/assignment/coupon_system/issuerequest/controller/CouponIssueRequestController.java)는 아직 Producer 직접 전송 후 ACCEPTED를 응답한다. `reserve()`는 API에 연결되지 않았다.
- [Relay](../../src/main/java/com/assignment/coupon_system/issuerequest/relay/CouponReservationRelay.java)는 processing 우선 재전송, Kafka 성공 후 LREM까지 구현했다. 반복 호출은 미연결이다. processing 제거는 DB 완료 증거가 아니다.
- [DB 처리기](../../src/main/java/com/assignment/coupon_system/issuerequest/service/CouponIssueProcessor.java)는 requestId 결과와 `(coupon_id,user_id)` 중복을 확인하고 수량·이력·결과를 같은 트랜잭션으로 저장한다. 최종 상태는 ISSUED/REJECTED뿐이다. Consumer는 메시지의 receivedAt을 처리기에 전달하지 않는다.

**빠진 부분**

예약 시점에 행사 기간·상태를 검사하는 원자적 경계, 예약 승인 근거, 예약 결과 조회와 DB 최종 결과의 연결, 사용자별 기존 requestId 조회, 운영 변경 이력, 영속성 계약이 없다. 현재 사용자 Set은 중복 여부만 알 수 있어 다른 requestId로 재신청한 사용자에게 기존 requestId를 돌려줄 수 없다. 기존 동기 API와 Kafka 직접 접수 API가 같은 쿠폰을 계속 발급하면 Redis 예약을 우회하는 경로가 생긴다.

**권장 정책과 이유 — 제안**

| 데이터 | 판단 기준 저장소 | 관리·조회 규칙 |
|---|---|---|
| 총 발급 한도·관리자 변경 | DB Coupon + 변경 이력/Outbox | 증가분·변경 ID·요청자·사유·버전·생성/적용 확인 시각 저장. 직접 SQL 변경을 정상 운영 절차로 사용하지 않음 |
| 예약 가능한 재고 | Redis stock | 아직 아무 예약에도 배정되지 않은 수량. DB의 총량-발급 완료 수로 대체하지 않음 |
| 예약 승인·사용자 중복 | 내구성을 갖춘 Redis 예약 원장 | requestId, couponId, userId, 서버 예약 시각, 승인 정책 버전/쿠폰 세대, 상태 저장. coupon/user→기존 requestId 매핑을 원자적으로 함께 관리하는 안 권장 |
| 최종 발급·사용·만료 이력 | DB IssuedCoupon + 요청 처리 결과 | 최종 결과는 DB 커밋으로 확정. Redis에 복사한 완료 상태는 조회용이며 지연 가능 |
| 취소 확정·반환 지시 | DB 요청 상태 원장 + 반환 Outbox | 발급과 취소를 같은 DB 경합 경계에서 직렬화. Redis 반환 여부는 별도 멱등 적용 상태로 추적 |
| 전달 진행 상태 | Redis pending/processing, Kafka offset | 운송 진행만 표시. 목록이 비었거나 lag0이어도 전체 예약의 최종 완료를 의미하지 않음 |

예약 원장은 Kafka 전달 후에도 바로 삭제하지 않는다. DB 결과가 없을 때 “미반영/조사 중”을 추적하고 미전달 예약도 복구할 수 있어야 한다. 최종 DB 이관·재전달 보존기간·감사 보존기간을 충족한 뒤 삭제 정책을 별도로 정한다. 임의 TTL로 중복·취소·변경 ID를 먼저 지우지 않는다.

예약 Lua에 서버 기준 기간·접수 활성 상태·정책 버전 확인을 포함하는 안을 권장한다. API에서 DB를 먼저 읽기만 하면 확인과 Redis 예약 사이에 관리자가 종료할 수 있다. DB 정책 변경도 변경 명령/전달 기록을 거쳐 Redis에 적용하고, 일반 접수 중지의 효력은 Redis 적용 시점으로 정의한다. DB 변경 요청과 즉시 전역 중지가 같다는 약속은 하지 않는다. 긴급 즉시 중지는 별도 차단·동기화 절차가 필요하다. `[시작, 종료)` 같은 경계 규칙과 시계 기준도 통일한다.

선착순 기준은 Redis에서 신규 예약이 성공한 순서로 제안한다. 필요하면 Lua에서 예약 순번을 함께 저장한다. Kafka 순서는 이후 전달 순서이므로 이전 구조의 “Kafka 기록 순서” 정의를 그대로 가져오지 않는다. 승인된 예약의 발급 권리는 이후 Consumer 처리 순서와 구분한다.

불변식은 쿠폰별로 다음과 같이 잡는다. `Tdb`는 DB 승인 총량, `Tr`는 Redis에 적용 완료된 총량, `H`는 예약되어 차감됐고 아직 반환하지 않은 수량, `R`은 예약 가능 재고다.

- 정상 운영에서 `R = Tr - H`, `R >= 0`. H에는 DB 발급 완료·미반영·조사 중·취소 확정 후 반환 대기가 모두 들어간다. DB 반영 완료 자체는 재고를 반환하지 않는다.
- 증량만 허용하는 첫 버전에서 `Tr <= Tdb`. 차이는 아직 Redis에 적용되지 않은 증량이며 가용 재고로 먼저 판매하지 않는다.
- 정합성 비교는 ID로 수행한다. pending/processing에서 사라졌지만 Kafka/DB에 남은 요청도 있으므로 `H = pending 길이` 또는 `총량 - DB 완료 = R`로 계산하지 않는다.

**검증할 테스트**

예약/발급 상태 구분, 동일 requestId 응답 유실 후 재시도, 다른 requestId의 동일 사용자 재신청, 내용 충돌, 기간 경계·정책 변경과 예약의 경쟁, Redis 부족/사용 불가일 때 DB 수량으로 우회하지 않음, 같은 쿠폰의 구 동기/직접 Kafka 경로 차단. 정지 상태의 일관된 스냅샷에서 위 불변식과 전체 ID 매핑을 확인한다.

#### 2. 행사 중 재고 추가

**현재 구현**

`initStock()`은 DB issuedQuantity를 0으로 만들고 상태를 ACTIVE로 바꾸며 Redis stock을 totalQuantity로 덮어쓰고 사용자 Set을 삭제한다. 예약 Hash·pending·processing·기존 발급 이력은 삭제하지 않는다. `@Transactional`은 이 DB 변경과 Redis 변경을 하나의 원자적 커밋으로 묶지 않는다. `getCouponStock()`은 DB totalQuantity-issuedQuantity만 반환한다.

**빠진 부분**

증량 명령·멱등 ID·변경 감사 이력·실패 재전달·Redis 적용 확인·버전이 없다. 관리자 변경 중 DB/Redis 한쪽만 성공할 수 있고, 현재 초기화를 행사 중 호출하면 이미 예약/발급한 수량을 다시 판매할 수 있다.

**권장 정책과 이유 — 제안**

1. 관리자 요청은 고유 changeId, couponId/세대, 양수 delta를 받는다. DB 트랜잭션에서 쿠폰 행 잠금 또는 원자적 UPDATE로 총량 증가, 불변 변경 이력과 Outbox를 함께 커밋한다. changeId 고유 제약으로 동일 요청 재시도 시 증가하지 않으며, 같은 ID의 다른 payload는 충돌 처리한다.
2. DB 커밋 후 별도 전달자가 변경 이벤트를 Redis로 보낸다. DB 성공 후 종료해도 Outbox가 남는다. 전송 전 DB rollback이면 이벤트도 없다. 사용자 예약마다 DB 쓰기를 넣는 설계가 아니라 관리자 변경 경로에만 적용한다. [AWS의 Transactional Outbox 원칙](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)을 적용한 제안이다.
3. Redis Lua에서 쿠폰 세대·재고 초기화 상태·자료형/정수 범위와 changeId/payload를 검사하고 `INCRBY(stock, delta)` + 적용 총량/변경 기록 저장을 함께 수행한다. stock이 없으면 INCRBY로 새 stock을 만들지 않고 복구 필요로 중단한다. 기존 예약·사용자·전달 목록은 유지한다.
4. Redis 성공 및 선택한 내구성 확인 후 DB의 전달 상태를 APPLIED로 갱신한다. Redis 성공→DB 상태 갱신 사이 종료 또는 타임아웃이면 같은 changeId 재전달로 중복 증량을 막는다. 관리자 화면은 DB 승인과 Redis 적용 확인을 분리한다. DB Outbox의 APPLIED는 당시 확인 기록이며 Redis 데이터 유실 이후 현재 반영의 증거로는 부족하다.
5. 첫 버전은 증가만 허용한다. 서로 다른 증가 이벤트는 delta와 적용 ID 집합으로 처리해 순서가 바뀌어도 누락하지 않는다. 단순히 “가장 큰 버전보다 작으니 무시”하면 중간 증량을 잃는다. 순차 버전을 쓰려면 빈 버전을 보류·재요청하고 연속 적용 지점을 유지해야 한다. 감소·기존 예약 회수는 별도 설계 대상이다.

예: 총량100, 확정 예약70(그중 DB 반영20)이면 Redis 잔량30이다. 총량을20 늘리면 Redis는50이어야 한다. `120-20=100`으로 덮어쓰면 DB 미반영50건을 다시 판매한다.

`initStock()`은 운영 증량·복구 경로에서 금지하고, 신규 쿠폰의 최초 초기화와 격리된 실습 리셋을 분리한다. 최초 초기화도 예약/발급이 없는 새 쿠폰·세대에 한 번만 허용하며 두 초기화 요청과 첫 예약의 경쟁을 막아야 한다. 같은 쿠폰을 재사용하며 사용자 Set만 비우는 초기화는 하지 않는다. 재고 조회 API는 Redis `reservableQuantity`와 DB `totalLimit/issuedQuantity`, 적용 대기 증량, 관측 시각을 구분한다. Redis 불가 시 예약 가능 수량은 UNKNOWN/조회 실패이지 DB 차이값이 아니다. 서로 다른 시점의 조회 값을 원자적 스냅샷처럼 표시하지 않는다.

**검증할 테스트**

동시 예약+증량의 최종 수량, 여러 관리자 동시 증가, 동일 changeId 중복/다른 payload, 변경 순서 역전, DB 커밋 직후 종료, Redis 성공 직후 응답 유실·APPLIED 갱신 전 종료, Redis 연결 실패/재시작 후 재전달, stock 누락·잘못된 세대, 초기화 재호출 차단. 적용 ID 유실을 포함한 복구에서는 아래 전체 재구성 절차도 검증한다.

#### 3. 예약 후 DB 반영 실패

**현재 구현**

DB 처리기는 처리 시점의 `coupon.isAvailable()`을 검사하고, UPDATE도 `status=ACTIVE AND issuedQuantity<totalQuantity`를 요구한다. 종료/비활성/소진을 모두 REJECTED로 저장한다. 예약 당시 승인 근거를 전달받지 않으며 취소 상태도 없다. Consumer 오류 처리기는 `CommonContainerStoppingErrorHandler`라 처리 예외 시 컨테이너를 멈춘다. 자동 재시도·재개는 아직 없다. 기존 동기 경로의 `rollbackIssue()`는 Set 제거와 stock 증가를 별도 명령으로 실행하므로 새 비동기 취소에 재사용하지 않는다.

**빠진 부분**

승인된 예약을 존중하는 별도 DB 처리 규칙, 오류 분류·운영 조사 상태·명시적 재개, 취소와 발급의 경쟁 방지, 반환 명령 멱등성, 완료 결과 동기화가 없다. 현재 reserve가 기간·상태를 보지 않으므로 DB의 검사만 지우는 변경도 안전하지 않다.

**권장 정책과 이유 — 제안**

| 분류 | 예약/DB 처리 | 재고 반환 |
|---|---|---|
| 일시 장애: DB 연결 실패·deadlock·일시 timeout | 예약 유지, 같은 requestId로 재처리. 제한된 backoff·알림·명시적 재개를 설계. 횟수 초과는 조사 대기이지 자동 최종 거절이 아님 | 하지 않음 |
| 커밋 여부 불명: 연결 단절·응답 유실 | DB가 회복된 뒤 새 트랜잭션으로 requestId 조회/멱등 재처리. 한 번의 조회 부재는 미커밋 확정이 아님; 기존 실행과도 DB 제약·직렬화로 경쟁 제어 | 하지 않음 |
| 영구 오류 의심: 누락/손상 payload·정책 버전 불명·불변식 위반 | 원본 ID/payload/오류/시도 이력을 보존하고 조사·격리. 수정·재반영을 기본으로 함. 이미 승인한 예약을 조용히 REJECTED로 바꾸지 않음 | 조사 중 하지 않음 |
| 명시적 취소 확정 | 아래 DB 취소 절차와 반환 Outbox 적용. 승인 주체·사유를 기록 | DB 취소가 확정되고 미발급임을 직렬화 경계에서 확인한 뒤 정확히 한 번 |

DB 상한·고유 제약·발급/결과의 단일 트랜잭션은 유지한다. 승인 예약인데 상한에 걸리는 것은 일반 SOLD_OUT이 아니라 적용 누락·우회 발급·정합성 이상 후보로 취급한다. 동일 requestId의 기존 ISSUED는 성공 결과 그대로 반환한다. 다른 requestId에 이미 사용자 발급 이력이 있으면 새 예약을 임의 성공으로 묶지 말고 조사한다. Redis 예약 승인 없이 직접 보내던 메시지와 새 승인 메시지를 토픽/스키마 종류 또는 명시적 모드로 구분하고, 검증된 내부 전달자만 승인 메시지를 생성한다. requestId와 클라이언트 시각만으로 승인 증거가 되지 않는다.

**행사 종료·상태 변경 정책 제안:** 예약 당시 유효하게 승인된 요청은 정상 행사 종료나 이후 일반 접수 중지에도 발급한다. 행사 상태는 새 예약 허용 여부이고 기존 권리 취소와 분리한다. DB의 현재 ACTIVE/현재 시각 검사를 그대로 재사용하지 않고 예약 시각·승인 정책 버전·세대를 근거로 처리한다. 이를 위한 메시지와 Processor 인자 변경을 함께 한다. 긴급 전면 철회는 명시적 취소 절차로 다룬다. 첫 버전은 자동 취소 없이 조사·복구를 우선하는 안을 권장한다. 현재 만료일은 `IssuedCoupon.issue()` 실행 시각+validDays다. 사용 가능 기간을 발급 완료 기준으로 유지할지 행사 고정 만료일로 할지는 별도 미확정이며 예약 후 지연으로 권리가 소멸하지 않도록 명시해야 한다.

**취소를 허용할 때의 필수 경계 — 설계 제안, 아직 미구현**

1. DB에 requestId별 처리 상태 원장을 두고 발급/취소 양쪽이 같은 행을 잠그도록 한다. 행이 없으면 requestId 고유 키로 생성 경쟁을 처리한 뒤 잠근다. 잠금 없는 “발급 이력 없음” 조회만으로 취소를 확정하지 않는다. 발급 수량·이력·ISSUED 전환도 이 잠금과 같은 트랜잭션에 둔다.
2. ISSUED가 먼저 커밋됐으면 이 미발급 취소는 거절한다. CANCELLED가 먼저 커밋됐으면 모든 늦은 발급 메시지는 종료 상태를 확인하고 발급하지 않는다. 취소 tombstone은 Kafka 재전달/보관·재시도 기간 이상 보존한다. 이미 발급된 쿠폰 회수는 사용 여부까지 보는 별도 업무다.
3. CANCELLED 확정과 고유 refundId의 반환 Outbox 저장을 같은 DB 트랜잭션으로 커밋한다. 취소 요청만 받았거나 DB가 불명인 상태에서는 반환하지 않는다.
4. Redis Lua는 예약 존재/세대/미반환 상태와 refundId를 확인해 stock+1, 반환 완료 및 취소 상태를 함께 기록한다. 실패/응답 유실 시 동일 ID로 재처리한다. 예약이 사라졌으면 무조건+1 하지 않고 복구 대상으로 둔다. DB 취소 후 Redis 실패는 반환 대기이며 안전하게 적게 판매하는 상태다.
5. Redis의 processing에서 먼저 지우는 것은 취소가 아니다. Kafka에 이미 보낸 메시지를 회수할 수 없으므로 늦은 전달 방지는 DB CANCELLED가 책임진다. 첫 버전은 사용자 중복 기록을 유지해 취소 후 재신청은 허용하지 않는 안을 권장한다. 재신청을 허용하려면 사용자 매핑의 현재 requestId까지 비교해 원자적으로 해제하고 이전 요청 tombstone은 유지해야 한다.

격리도 삭제가 아니다. 첫 버전은 문제가 있는 처리 흐름을 중단하고 운영자가 조사·재개하는 방식이 단순하다. 격리 저장 후 다음 offset으로 진행하려면 원본을 내구성 있게 저장하고 추적 가능한 결과/재처리 경로를 갖춘 뒤에만 offset을 넘긴다. 순서를 건너뛰는 정책을 별도 합의한다. 단일 글로벌 processing의 오류 하나가 모든 쿠폰 전달을 막을 수 있다는 운영 한계도 기록한다.

**검증할 테스트**

DB 중단 동안 예약 유지→복구 후 전량 발급, DB 커밋 직후 응답/offset 유실→추가 발급 없음, deadlock/timeout/영구 오류 분류, 격리 전후 ID 추적, 예약 후 행사 종료/일반 중지에도 발급, 승인 근거 없는 메시지 차단, DB 상한 위반 조사. 취소 도입 시 발급과 취소의 동시 실행·행 생성 경쟁·늦은 메시지·취소 직후 종료·반환 실패/중복/순서 역전까지 확인한다. 강제 종료 시점이 실제 DB 커밋 뒤인지 독립 조회 등으로 확인한다.

#### 4. Redis 장애와 예약 응답의 내구성

**현재 구현·런타임 확인**

2026-10-04 기존 `coupon-redis`에 읽기 전용 CONFIG GET/INFO replication을 수행했다. `appendonly=no`, `appendfsync=everysec`, `save=3600 1 300 100 60 10000`, `maxmemory=0`, `maxmemory-policy=noeviction`, replica0이다. Compose는 CPU0.5/256MiB와 로컬 named volume을 둔다. AOF가 꺼져 있으므로 everysec 값만으로 AOF 보호가 있다고 볼 수 없다. Lua 성공 뒤 fsync/복제 확인 코드는 없다. 현재 키는 단일 Redis용이고 글로벌 pending/processing을 사용한다.

**빠진 부분**

확정 응답한 예약을 어떤 장애까지 보존할지, 복제·영속성 확인·쓰기 실패 시 응답 규칙, 디스크 유실 복구 원본, 재구성 중 신규 예약 차단, 이전 작업자 차단 세대, 복구 검증 절차가 없다. Redis가 유일하게 가진 Kafka 미전달 예약을 잃으면 DB와 Kafka만으로는 그 ID를 알아낼 수 없다.

**권장 정책과 이유 — 제안**

- 확정 예약은 수용한 장애 범위 안에서 RPO0을 목표로 제안한다. 범위를 앱 종료만, Redis 프로세스/호스트 중단까지, 디스크/노드 유실·failover까지로 나눠 확정해야 한다. 복구시간 목표는 운영자가 정할 미확정 값이다. 현재는 “앱 종료 후 Redis 데이터가 남아 있는 경우 재시도 가능” 범위만 설계·일부 검증했다.
- RDB는 시점 스냅샷이어서 최근 쓰기를 잃을 수 있고 AOF everysec도 최근 약1초 쓰기의 유실 가능성이 있다. 프로세스/호스트 중단과 보존된 디스크를 범위로 삼는 첫 후보는 AOF always 및 영속 저장소·쓰기 오류 감시다. fsync 응답 경계와 실제 장애 주입을 검증해야 하며 디스크 자체 손실 보장은 아니다. [Redis persistence 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).
- 노드/디스크 손실까지 포함하면 독립 장애 영역의 복제본·AOF와 성공 응답 전 확인 및 안전한 승격 정책이 필요하다. Redis7.2+의 WAITAOF는 후보지만 명령만 넣으면 보장이 완성되지는 않는다. Lua 이후 같은 연결의 앞선 쓰기에 대한 local/replica fsync 수를 확인해야 하고, timeout 반환도 요구 수 미달이면 성공으로 해석하면 안 된다. Lua 안에서 기다리는 방식도 아니다. 재시도가 다른 연결에서 기존 예약을 읽기만 했다면 그 연결의 확인만으로 원래 쓰기의 내구성을 증명할 수 없으므로 재확인용 쓰기/영속 오프셋 추적까지 설계해야 한다. [WAITAOF 공식 문서](https://redis.io/docs/latest/commands/waitaof/).
- Redis 비동기 복제나 WAIT만으로 강한 일관성·failover 무유실이 보장되지는 않는다. 승격 후보/쓰기 차단 조건과 실제 장애 모델까지 검증한다. [Redis replication 공식 문서](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/). 선택한 Redis 구성으로 필요한 장애 범위를 못 맞추면 “예약 확정”의 보장 범위를 낮춰 명시하거나 응답 전 별도 내구성 원장을 도입하는 계약 변경이 필요하다. 사용자 방향을 임의로 Kafka ack 대기로 바꾸지 않는다.
- Redis timeout/영속성 확인 timeout은 “예약 실패 확정”이 아니라 결과 불명일 수 있다. 같은 requestId 재시도/조회로 확인하고 자동 재고 반환은 하지 않는다. 새 UUID로 재신청을 유도하지 않는다. 아직 DB 조회 API 구현까지 확정한 것은 아니며 조회 계약·운영 대조 경로를 먼저 정한다.
- 예약·사용자·변경 ID·취소/반환 마커는 eviction/독립 TTL 삭제 대상이 아니다. 용량·디스크·복제 상태가 보장 범위를 벗어나면 신규 예약을 차단한다. noeviction이어도 컨테이너 OOM kill 위험은 남는다. Lua는 다른 명령과 섞이지 않지만 실행 중 오류의 기존 쓰기를 롤백하지 않으므로 자료형/값 검증과 오류 후 정합성 조사도 필요하다.

**미반영 예약까지 포함한 복구 기준 — 제안**

1. 신규 예약·관리자 증량 전달·반환 전달·기존 relay/Consumer를 일시 정지하고 이전 작업자가 다시 쓰지 못하게 격리한다. 쿠폰 세대/복구 epoch를 관리해 이전 작업의 적용을 막는다. 이것은 기존 유효 예약을 버리는 근거가 아니라 통제된 재생 경계다.
2. Redis 영속 원장/복제본, DB 발급·취소·변경 Outbox, Kafka의 아직 처리되지 않은 승인 이벤트를 공통 기준점까지 수집한다. requestId·changeId·refundId로 중복을 제거하고 예약 승인 근거·세대·payload를 대조한다. DB에 없는 예약도 반드시 포함한다.
3. DB의 Tdb와 모든 복원된 예약에서 재고를 재구성한다. DB ISSUED는 이미 Redis에서 차감했던 같은 예약과 중복 차감하지 않는다. 미발급 유효/조사 중 예약도 차감한다. DB CANCELLED는 반환 완료로 통일해 재구성할 수 있지만, 그 경우 해당 refundId를 적용 완료로 기록해 늦은 반환이 다시 더하지 않게 한다. 적용한 증량 changeId도 함께 복원한다. 과거 APPLIED 이벤트를 모두 INCRBY로 다시 보내거나 마커만 믿고 건너뛰지 않는다.
4. 예를 들어 DB 총량을 새 Redis 기준 총량으로 삼았다면 그 기준점까지의 changeId를 적용된 것으로 함께 기록하고 이후 변경만 재생한다. stock·사용자 매핑·예약·적용 마커를 일관된 새 세대로 구성한다. 처리 결과가 없는 유효 예약은 pending으로 재구성하되 원래 순번을 보존한다. Kafka에 이미 있는 요청이 다시 전달돼도 DB 멱등성으로 수렴해야 한다.
5. 전체 확정 예약의 ID 집합과 DB 최종 상태/미반영 원장, R/Tr/H 및 발급 수량·이력의 일치를 확인한 뒤 재개한다. 복원할 원본이 없어 확정 예약의 완전성을 증명할 수 없으면 자동 재개하지 않는다. DB 완료 수만 맞거나 lag0인 것으로 복구 성공을 선언하지 않는다.

**검증할 테스트**

예약 응답 직후·Kafka 전송 직전 Redis 비정상 종료, AOF fsync 확인 전후 응답 유실, replica 장애/승격·필요 복제 수 부족, 스냅샷 이후 예약 누락, 디스크 가득 참·쓰기 실패·OOM, 복구 중 오래된 작업자 재접속. 증량/취소 반환 적용 마커와 재고가 함께 복구되는지, Kafka 미전달 예약까지 전량 복원되는지, 복구 후 예약·발급·취소·재고의 ID별 정합성을 확인한다. 현재 약0.8ms 예약 p95는 AOF 비활성 조건이므로 내구성 설정 변경 후 다시 측정해야 한다.

### 첫 버전 확정 범위 — 2026-10-05

**10/7 후속 교정:** 행사 중 정책 변경과 동일 쿠폰 ID 재사용을 지원하지 않으므로 정책 버전 저장·전달은 필수가 아니다. 아래 당시 버전 전달 계획은 현재 필수 범위에서 제외한다. Redis 승인 시각을 보존해 DB 발급에 사용하는 연결을 우선한다. 기존 승인 근거 테스트의 버전 검증 결과는 당시 구현 증거로 보존한다.

사용자가 구현 범위를 확정했다. 앞의 넓은 운영 설계와 미확정 정책 목록보다 이 절을 우선한다. 목적은 사용자 신청부터 최종 발급까지 연결하고, 빠른 예약과 장애 후 확실한 최종 발급을 실제로 검증하는 것이다. 이번 갱신은 범위·순서 정리이며 코드·설정 변경이나 테스트 실행은 하지 않았다.

**확정 정책**

- 행사 시작 전에 수량·기간을 고정한다. 행사 중 증량/감량·예약 취소를 지원하지 않는다. 관리자 변경 Outbox·취소 원장·재고 반환 설계는 이번 필수 구현에서 제외한다.
- Redis가 정상 승인한 예약은 정상 행사 종료 후에도 발급한다. 예약 가능 여부는 신규 예약 시점에 판단한다.
- DB 장애에는 예약을 유지하고 복구 후 같은 requestId로 재처리한다. 자동 재고 반환과 자동 최종 거절을 하지 않는다. 영구 오류 자동 분류·격리는 구현하지 않고, 처리 중단·로그·원인 수정 후 재개로 시작한다.
- 전달 작업자는 전체 앱 구성에서 하나만 실행한다. 다중 작업자 소유권·분산 리더 선출을 도입하지 않는다.
- 사용자에게 Redis 예약 확정을 응답하고 DB 발급 커밋 뒤 사용 가능한 상태를 조회로 제공한다. Kafka ack 또는 DB 완료를 기다리는 접수 API로 되돌리지 않는다.
- Redis 보존 설정과 재시작 복구는 이번 범위에 포함한다. 다중 노드 장애·복제 승격은 범위 밖이다.

**검증할 장애 범위 — 구체화 제안**

단일 Redis와 보존되는 로컬 볼륨에서 앱 프로세스 강제 종료, Redis 프로세스/컨테이너 강제 종료·재생성 후 같은 볼륨 복원, DB 일시 중단을 실제 주입한다. 성공 응답한 모든 예약의 복원·최종 발급을 합격 기준으로 둔다. 호스트 전원 장애, 디스크 손실/손상, 볼륨 삭제, 다중 노드 failover까지 검증했다고 주장하지 않는다. 실제 시험한 장애와 저장장치 가정을 결과에 기록한다.

Redis AOF 활성화 + appendfsync always + 영속 볼륨을 첫 설정 후보로 삼고, 성공 응답 경계와 재시작 데이터를 검증한다. 아직 설정을 바꾼 상태가 아니다. AOF everysec에서의 약1초 유실 가능성을 예약 확정 보장으로 허용했다고 간주하지 않는다. 근거는 앞 절의 Redis persistence 공식 문서와 같으며, fsync가 모든 종류의 저장장치 장애를 해결한다는 의미는 아니다. 기존 AOF 비활성 예약 성능 수치는 설정 변경 후 비교 기준으로만 보존한다.

**구현 순서와 완료 기준**

| 순서 | 구현 범위 | 확인할 것 |
|---|---|---|
| 1 | 승인 근거 저장 | Lua가 판정에 사용한 Redis 시각·정책 버전을 예약에 저장하고 조회 DTO·Kafka 메시지로 보존. 재시도는 최초 값을 유지. 정책은 행사 동안 불변으로 유지하며 버전1에 대응하는 수량·기간을 보존; 범용 정책 변경 이력 기능은 만들지 않음 |
| 2 | DB 발급 규칙 변경 | 승인된 예약 전용 경로에서 행사 종료 후에도 발급. 신뢰 가능한 내부 예약 메시지와 고정 정책을 검증하고, DB 상한·사용자/요청 ID 중복 방지·단일 트랜잭션은 유지. 구 직접 발급 경로가 같은 행사 재고를 우회하지 못하게 함 |
| 3 | 단일 작업자·예약 API·결과 조회 연결 | processing 우선 반복 처리, 실패 시 보존·대기/중단·재개. 예약 API는 Redis 승인 후 응답. 조회는 requestId로 DB ISSUED를 우선 확인하고, DB에 아직 없고 Redis에 예약이 있으면 RESERVED를 반환. 조회 실패를 미신청/발급 실패로 단정하지 않음 |
| 3의 선행 조건 | Redis 보존 설정·안전한 행사 준비 | 예약 API 활성화 전에 영속 설정을 적용하고 실행 설정을 확인. 신규 행사 최초 초기화만 허용하고 기존 initStock 재초기화/행사 중 변경 경로를 차단. 재시작 시 재고를 DB 완료 수로 덮어쓰지 않음 |
| 4 | 실제 장애 복구 | 별도 테스트 앱·Redis/Kafka/DB에서 예약 후 앱 종료, Kafka 성공 후 processing 제거 전 종료, DB 커밋 후 offset 전 종료, Redis 재시작, DB 장애와 복구. 모든 확정 requestId의 최종 발급·중복 없음 확인 |
| 5 | 전체 부하 비교 | stock100000, 100/s20초→1200/s10초→100/s30초, timeout5초·재시도 없음. 실제 유입·미전송, 예약 응답/최종 발급시간, pending/processing/Kafka lag·DB 완료율을 분리하고 마지막 ID까지 대조 |

현재 relay 단위 테스트와 기존 Kafka 장애 테스트는 개별 증거다. 새 승인 메시지를 사용하는 전체 경로의 장애 테스트를 대신하지 않는다. 초기화/예약 정책 테스트47개 통과는 출발점이며 최종 구조 완료가 아니다.

**최종 합격 기준**

예약 확정을 받은 requestId 집합이 DB ISSUED 결과와 발급 이력에 빠짐없이 대응하고, requestId·couponId·userId 및 발급 ID가 일치해야 한다. 중복 발급·미완료·예상하지 못한 REJECTED는0이다. 해당 행사 총량-Redis 잔량=고유 예약 수=DB issuedQuantity=발급 이력 수를 확인한다. 응답 불명 요청은 따로 최종 결과와 대조하며 실제로 예약됐으면 위 수량에 포함한다. pending/processing 소진과 lag0도 확인하되 그것만으로 합격하지 않는다. 장애 복구 완료시간과 큐 대기시간도 기록한다.

다음 즉시 작업은 승인 근거 저장이다. 현재 reserve()는 Redis TIME으로 기간을 검사하지만 reservedAt에는 Java 시각을 저장하므로, 먼저 이 두 시각을 일치시키고 정책 버전을 전달하는 최소 변경부터 진행한다. 사용자 직접 구현·코드 검토·명시 요청 시 테스트 실행이라는 실습 진행 방식은 유지한다.


### Kubernetes·EKS 학습을 위한 현재 연결 점검 — 2026-10-07

**10/8 후속:** 아래 당시 미연결이었던 Consumer→승인 시각 기반 DB 반영은 후속 12개 연결 테스트로 검증됐다. API·반복 Relay·조회·보존 설정 및 우회 경로 차단은 남아 있다. 아래 항목은 10/7 점검 이력이다.

- Redis 승인 시각은 이미 Hash와 CouponReservation에 있다. Relay가 메시지 receivedAt으로 옮기지만 Consumer→Processor에서 빠진다. 다음 작은 구현은 이 값의 전달과 고정 행사 기간에 대한 검증, 행사 종료 후 유효 예약의 발급이다. 멱등성·DB 상한·고유 제약·단일 트랜잭션은 유지한다.
- API는 아직 Producer 직접 전송이고, 단일 Relay 반복 실행과 requestId 상태 조회가 없다. 이전 initStock()·동기 발급이 같은 행사에 재고 재초기화나 우회 발급을 하지 못하게 연결 시 차단한다. Redis 영속 설정은 기록·설정 파일만 검토했으며 이번에 컨테이너 설정을 조회하거나 바꾸지 않았다.
- 앱 이미지 정의·Kubernetes 매니페스트·CI workflow는 현재 파일 목록에서 확인되지 않았다. Kubernetes 학습 전에 같은 앱 이미지를 api/relay/consumer 역할로 실행하도록 나누고 API 복제본 증가가 Relay 증가로 이어지지 않게 한다. 새 서비스 저장소를 분리하는 과제는 아니다.
- 처음에는 API 복제본을 늘리고 Relay·Consumer는 각각 1개로 둔다. Relay의 synchronized는 JVM 간 소유권을 보장하지 않으므로 단일 실행·Recreate 및 이전 프로세스 종료 확인 범위로 학습한다. 현재 토픽 1파티션·couponId 키이므로 Consumer 개수 증가를 DB 처리량 개선으로 간주하지 않는다.
- Compose 전체 경로의 장애·부하 기준을 확보하면 관리자 증량·자동 취소·정책 버전 관리 완성을 기다리지 않고 로컬 Kubernetes로 넘어간다. 준비 상태, 롤링 배포, API/Consumer 종료 복구, 수동 확장→HPA 관측 후 EKS의 외부 접속·배포·롤백으로 이어간다. 데이터 서비스 HA·다중 Relay는 별도 후속이다.
- 이 절과 공용 학습 계획은 설계이며 배포·클라우드 생성·시험 실행 결과가 아니다. 원시 결과와 기존 동기/Kafka 비교는 보존했다.
