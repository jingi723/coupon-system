# coupon-system — 선착순 쿠폰 발급 동시성 제어

대량 동시 요청에서 재고 초과 발급과 중복 발급 없이 선착순 쿠폰을 발급하는 것을 목표로,

- 구현 차이 비교 자료: [방어가 빠진 미커밋 코드의 결과](../../선착순_쿠폰발급_부하테스트/results/2026-10-01-sync-current/RESULTS.txt) — 현재 기준과 구분

## 문제와 해결 단계

1. 조회 → 검증 → 증가 흐름에서 발생하는 재고 초과·중복 발급 race를 동시성 테스트로 재현
2. 조건부 atomic UPDATE (`issuedQuantity < totalQuantity`일 때만 증가)로 재고 초과 방지
3. `(coupon_id, user_id)` unique constraint로 중복 발급을 DB 레벨에서 차단
4. Redis Lua 스크립트로 중복 체크·재고 확인·차감·등록을 원자 실행해 발급 판정을 DB 앞으로 이동,
   DB 저장 실패 시 Redis 재고 rollback

## k6 부하 실측 요약 (300 VUs · 30초, 로컬)

| 선착순 재고 100 | atomic UPDATE 경로 | Redis Lua 경로 |
|---|---|---|
| 처리량 | 3,325 RPS | 5,112 RPS |
| p50 / p95 | 88ms / 102ms | 56ms / 94ms |
| 재고 소진 후 거절의 DB 쓰기 | 조건부 UPDATE 실행 | Redis에서 거절해 DB 쓰기 0건 |
| 발급 수 | 정확히 100 | 정확히 100 |

재고가 남아 있는 구간은 두 경로 모두 DB 쓰기가 지배해 사실상 동일하다(약 665 RPS).
Redis 도입의 이득은 재고 소진 후 거절 트래픽이 DB 쓰기 경로에 들어가지 않는 데 있다. 쿠폰 유효성 확인 SELECT는 남아 있다.

### 앞선 도입 판단 — 2026-10-03 기록


**동기 기준, Kafka 연결과 Consumer 장애 복구를 거쳐 폭주 비교까지 확인했다. 현재 단일 Consumer 구성에서는 접수 응답은 빨라졌지만 최종 발급은 더 늦었다. 접수한 요청의 정합성은 유지됐고 DB 연결·행 락 대기는 관측 샘플에서 0이었다. 사용자 후속 선택에 따라 다음은 Redis 재고 예약→Kafka 전달→DB 반영 구조의 설계·검증이다. Kubernetes는 이후로 미룬다.**

2026-10-01 동기 기준 검토 당시 서비스 파일에 HEAD 대비 변경이 없고 Redis 판정과 DB 조건부 UPDATE 호출이 있음을 확인했다. 직전 sync-current 실험은 해당 방어가 빠진 미커밋 코드를 대상으로 했다. 그 데드락·수량 불일치를 현재 Redis/조건부 UPDATE 버전의 결과로 합치지 않는다.

재고가 남아 있는 유효 신청을 DB가 바쁘다는 이유만으로 거절하는 것은 이번 실습의 서비스 목적을 충족하지 않는다. 이벤트 시작에 몰리는 신청을 수용하고 DB를 보호하기 위해 요청 접수와 발급 처리를 큐로 분리하는 방향을 검증한다. 실제 유실이나 서버 다운을 먼저 재현해야만 큐를 검토할 수 있는 것은 아니다.

현재까지 확인된 것은 DB 연결·행 락 대기와 응답 지연이다. 서버가 받은 요청의 유실은 관측하지 않았다. 큐는 DB 자체의 처리량을 자동으로 늘리는 기술이 아니라, 순간적인 초과 유입을 보관하고 처리 속도를 조절하는 수단으로 검토한다. Kafka를 실습 대상으로 사용하되 그 효과는 이후 동일 조건 비교로 확인한다.

### 실제 Kafka 연결 — 실행 결과 확인, 2026-10-02

### 후속 성능 검증 후보 — Consumer 처리 비용 분리

**후속 상태(2026-10-03):** 아래 계측은 완료했으며 결과는 이 문서의 「Consumer 비용 계측 결과」에 기록했다. 현재 단일 Consumer에서는 DB 서비스 경로가 지배적이었고 RECORD offset 커밋은 주원인이 아니었다. 아래 목록은 당시 비교 후보를 보존한 것이다.

2. RECORD 커밋 비용이 유의미하면 ack-mode만 BATCH로 바꾸는 비교를 후보로 삼는다. DB는 한 건씩 처리하는 조건을 유지해 offset 커밋 묶음의 효과만 본다. 이는 DB INSERT 일괄 처리와 다르다. 중단 시 이미 DB에 저장된 여러 레코드가 재전달될 수 있으므로 바뀐 커밋 경계에 맞춰 중복 발급·미완료 검증도 수행해야 한다. 아직 변경하거나 효과를 측정하지 않았다.
3. DB 구간이 주된 비용이면 쿼리 왕복·불필요한 조회 등 근거가 확인된 항목부터 하나씩 비교한다. 현재 파티션 1개에서 Consumer 수만 늘리는 방식은 해당 파티션을 병렬 소비하게 하지 않는다. 병렬화는 쿠폰별 순서와 동일 재고 행 경합을 함께 검토하는 별도 설계다.
4. 회복 기준을 끝까지 확인하려면 후속 비교에서 평상시 유입 관찰 구간을 늘리고 조건을 명시한다. 요청을 중단한 뒤 lag 0을 오래 관찰하는 것으로 새 요청 지연의 회복 판정을 대신하지 않는다.

커밋 단위와 파티션 할당은 [Spring Kafka 공식 문서](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html)를 참고했다(2026-10-03). RECORD는 레코드 처리 후, BATCH는 poll에서 받은 레코드 처리 완료 후 offset을 커밋하며 기본 syncCommits는 true다. 현재 병목의 원인으로 확정한 내용은 아니다.

- System.nanoTime으로 구간을 측정하고 전체 호출의 숫자/요청 ID를 메모리에 보존한 뒤 종료 때 일괄 기록한다. 요청당 로그는 출력하지 않는다. 유한 버퍼의 초과·계측 예외·스레드 ID·중첩을 검사한다. 원시 구간에서 p50/p95/p99·누적시간·횟수와 초당 DB 프록시 정상 반환 건수를 계산한다.
- 고정 부하: 재고 100000, 고유 사용자/requestId, 100/s 20초→1200/s 10초→100/s 30초, timeout 5초, 재시도 없음, VU 50/6500/1000. 기존 overload 스크립트를 재사용한다. 전송 절대 시각으로 구간을 나누고 목표 17000·실제·미전송을 따로 센다.
- 실행 순서 OFF1→ON1→ON2→OFF2. OFF도 같은 테스트 앱/외부 관측을 사용하되 내부 타이밍 프록시/콜백은 설치하지 않는다. OFF/ON의 적체 구간 DB 완료율과 전체 소요시간 편차를 비교한다. 양 ON 처리량이 양 OFF보다 10% 이상 낮으면 오버헤드 가능성을 표시하며, 범위가 겹치면 비용을 정밀히 분리했다고 주장하지 않는다. 10%는 이번 시험용 판정값이다.
- 적체 판정: 5초 구간의 모든 약250ms 샘플 lag>=500이고 15개 이상 샘플이 있는 구간. 시간대별 DB 완료율은 독립 조회한 커밋 결과의 최초 관측 건수/초(OFF/ON 공통)와 실제 프록시 반환 건수/초(ON)를 함께 제시한다. 시작/끝 경계 조회 오차를 명시한다.
- 동일 Consumer 스레드의 동일 적체 창에서 DB·offset·poll 구간을 잘라 계산한다. DB는 Listener에, DB commit 콜백은 DB에 포함되므로 중첩 합산하지 않는다. 창 전체에서 DB/offset/poll 합집합을 뺀 잔여를 기타 루프·계측·스케줄링으로 보고한다. CPU/외부 관측/heartbeat 시간을 이 분모에 더하지 않는다.
- 4회 모두 외부 DB 결과 약250ms, 연결 대기 약250ms, 행 락/DB 쓰기 카운터 약1초, JVM ProcessCpuTime 및 Docker DB CPU/Block I/O를 수집한다. 조회 간격 실제 분포·시계 불연속·결과 관측 누락을 검증한다. DB 전역 지표는 해당 시험만의 비용으로 단정하지 않는다.
- 기존 앱/브로커는 유지하고 별도 Kafka 브로커/그룹과 앱 포트를 사용한다. MySQL/Kafka CPU 1개·1GiB, Hikari 10, Consumer 1, 파티션1, RECORD를 유지하고 런타임 설정을 보존한다. 앱은 기존과 같은 JVM 기본 자원 제한이며 다른 호스트 작업과 캐시 차이를 기록한다.
- 종료 조건: 신규 요청 종료 후 모든 결과/이력/수량/ID 매핑 검증 및 lag=0, 앱 HTTP/DB 무활동과 수량 안정 35초. 성공/거절/불명 요청을 모두 대조한다. lag=0만으로 정합성을 판정하지 않는다.
- 비용 판단: 같은 적체 창에서 두 ON 실행 모두 가장 큰 비중인 구간을 우선 병목 후보로 한다. 50% 초과이면 지배 비용, 20% 이상이면 비교할 가치가 있는 비용으로 표시한다. 이는 인과관계 확정이나 변경 후 개선 보장이 아니다. 결과에 따라 후속 비교 하나만 추천하고 이번에는 변경하지 않는다.

**아직 분리하지 못한 비용:** DB 내부의 JDBC 왕복/JPA/flush/스케줄링, commit의 순수 디스크 동기화와 네트워크, broker 내부 offset 처리 비용이다. 연결 대기·행 락 대기 샘플0, DB CPU 평균 약19~22%만으로 DB 여력이 충분하다고 판단하지 않는다. OFF/ON 처리량 범위가 겹치며 일관된10% 이상 계측 저하는 없었지만, 오버헤드0이나 정확한 비율은 확인하지 못했다. 캐시/JIT/호스트 경쟁/순서 효과가 남는다.

**후속 성능 비교 후보:** Kafka를 제외한 DB 전용 순차 벤치마크에서 트랜잭션당1건 vs10건을 비교한다. 두 군 모두 같은 JDBC 실행기로 SQL 개수·순서, 재고/고유 제약/멱등성/내구성/총 건수를 유지해 COMMIT 고정 비용을 분리한다. SQL 횟수·TPS·COMMIT 시간·정합성과 일괄 롤백 범위를 확인한다. 실제 서비스 배치 적용을 확정한 것이 아니며, 이번에는 이 변경이나 offset BATCH 실험을 하지 않았다.

**현재 작업 우선순위:** 사용자가 선택한 Redis 예약→Kafka 전달→DB 반영 구조의 설계를 먼저 진행한다. 위 DB 벤치마크는 이후 성능 실험 후보로 남긴다. 이번 계측은 기존 구조의 비교 기준이며 Redis 예약만으로 DB 저장·커밋 비용이나 최종 반영 지연이 줄어든다는 증거는 아니다.

원시 span은 메모리에 보존 후 부하·drain 종료 때 일괄 출력했다. 테스트용 프로세스·브로커만 종료했고 기존 앱/컨테이너와 DB 자료는 유지했다. 커밋·배포·조회 API 구현은 하지 않았다.
