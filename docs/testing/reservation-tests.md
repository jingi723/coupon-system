재고 10개에 서로 다른 사용자 50명 동시 신청 시 RESERVED 10건, SOLD_OUT 40건, 재고 0이며 예약·사용자·pending ID가 대응했다. 동일 requestId 동시 20회는 RESERVED 1건, ALREADY_RESERVED 19건으로 재고 차감과 pending 등록이 한 번이었다. 정상 예약, 소진 후 기존 예약 재조회, 사용자 중복, requestId 충돌, 소진, 미초기화, pending 키 자료형 오류, 잘못된 재고 문자열도 검사했다. 잘못된 자료형 전체 조합이나 Redis 장애 내구성 검증으로 확대하지 않는다.

현재 reserve()는 재고 차감·사용자 등록·예약 Hash·pending List 기록을 Lua로 수행한다. 당시에는 API·Kafka 전달 작업자와 연결되지 않았고 processingReservations()도 없었다. 이후 processing 키와 이동·조회 검증을 마쳤으며 아래 후속 결과를 참고한다. 동시성 테스트의 실행시간을 처리량 벤치마크로 쓰지 않는다.

사용자 후속 지적에 따라 작업자 연결 전에 예약 자체의 처리 성능을 측정할 수 있다. 충분한 재고와 고유 사용자·requestId로 실제 신규 예약 경로를 부하에 노출하고 목표/실제 호출률, 신규 예약 완료율, 호출 p50/p95/p99, 오류·대기, Redis CPU·메모리·pending 증가 및 최종 정합성을 본다. 재고 소진 후 빠른 거절이나 동일 요청 재조회 처리량을 신규 예약 처리량으로 합치지 않는다. 직접 서비스 호출 측정은 HTTP 응답 성능과 구분한다. 부하 단계는 기존 유입률과 폭주 프로필을 참고하고 실제 전송량을 기록한다. 이번 문서 검토에서는 성능 테스트를 작성하거나 실행하지 않았다.

연결 후에는 동일 부하 조건에서 접수/예약 응답, Kafka 전달 지연, 최종 DB 반영 지연·완료율과 적체 해소를 별도로 측정한다. 예약이 빨라져도 DB 반영 속도가 자동으로 개선되는 것은 아니다. 작업자 미연결 상태의 pending 누적은 drain 성능 검증이 아니다.

전달 작업자는 pending→processing 원자적 이동, Kafka 전송 성공 확인 후 processing 제거, 중단·전송 결과 불명 시 같은 requestId로 복구하는 경계를 설계한다. 현재 RPUSH 입력에는 LEFT에서 꺼내는 이동이 입력 순서를 유지한다. [Redis LMOVE 공식 문서](https://redis.io/docs/latest/commands/lmove/)(2026-10-03 확인)의 reliable queue 패턴을 참고했다. 단일 작업자 재시작 복구와 여러 작업자의 소유권·시간초과 회수는 구분하며 아직 구현·검증하지 않았다.

### Redis 예약 경로 장애 검증 계획 — 2026-10-14

실제 HTTP·별도 JVM·격리 Redis AOF always/MySQL/Kafka를 재사용하고 장애 주입은 테스트 BeanPostProcessor에만 둔다. 실제 LMOVE 반환 직후, 실제 Producer.send의 Future.get 성공 후/LREM 전, Consumer의 DB 트랜잭션 커밋 후/RECORD offset 전을 파일 기록과 독립 Redis/DB/offset 조회로 확인한 뒤 해당 자식 JVM만 SIGKILL한다. 재시작 시 같은 그룹·저장소를 유지한다.
