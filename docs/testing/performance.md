### Relay 구간 계측 계획 — 2026-10-14

서비스 로직을 변경하지 않고 테스트 전용 프록시로 단일 Relay의 processing 조회/claim/예약 조회, Producer.send 반환(실제 Kafka ack 대기 포함), processing 제거를 System.nanoTime으로 잰다. 가설은 Redis 명령 왕복 또는 Kafka ack 대기가 Relay 전달률을 제한한다는 것이며 fsync 자체로 단정하지 않는다. 메서드 반환 경계는 클라이언트 왕복 전체로 서버 실행·디스크 시간을 분리하지 못한다. Relay 외부 API/Consumer의 Redis 호출은 ThreadLocal로 제외한다. 성공 요청별 구간을 메모리에 보관하고 종료 시 기록하며 동일 스레드의 비중첩 구간만 Relay 전체와 대조한다. 계측 누락·호출 수·requestId 집합을 최종 예약과 비교한다.

AOF always/기존 자원/기존 60초 부하/5초 제한을 유지하고 OFF→ON→OFF→ON 4회 실행한다. 실행별 새 JVM/쿠폰, 같은 격리 인프라를 재사용하므로 순서·캐시·테이블 성장 효과는 남는다. OFF에서는 프록시를 설치하지 않으며 기존 외부 관측은 동일하다. ON/OFF의 전달률·Consumer 완료율·최종 p95·drain 차이가 반복 편차보다 작으면 뚜렷한 계측 영향이 검출되지 않았다고만 판단한다. 두 ON 실행에서 가장 큰 누적 구간이 일치하는지 확인하고 단일 원인 개선은 하지 않는다. 모든 승인 ID/수량/대기열 정합성을 기존 분석기로 검증하고 기존 개발 자원은 유지한다.

### Relay 준비 Lua 통합 비교 계획 — 2026-10-14

서비스 코드 변경 없이 테스트 전용 어댑터에서 processing 우선→없으면 pending claim→예약 필드 반환을 한 Lua 호출로 묶는다. production relayOne·Producer.send·processing 제거는 그대로 호출하며 테스트 어댑터만 기존 준비 메서드에 반환값을 연결한다. Lua는 롤백되지 않으므로 큐/Hash 자료형·필수필드·requestId·Java long 범위를 모두 쓰기 전에 검사하고 마지막에 LMOVE한다. 동적 Hash 키를 읽는 현재 단일 Redis 전용 시험이며 Redis Cluster 지원으로 해석하지 않는다. 오류 시 모든 키가 유지되는지 실제 Redis DUMP로 대조하고, 기존 실제 claim/ack/DB 커밋 경계 종료·DB 실패 복구4개를 통합 경로에서 재실행한다.

가설은 Redis 왕복 감소가 준비 시간을 줄이는지다. AOF always·자원·부하·계측 ON을 동일하게 유지하고 기존→Lua→Lua→기존 순서(ABBA)로 반복한다. 캐시·데이터 증가·공유 디스크 편차는 남는다. 두 경로에 같은 바깥 Relay/Redis/Producer 계측을 적용한다. Lua 모드의 peek 구간에 단일 Lua 및 역직렬화가 들어가고 findReservation은 메모리 스냅샷 반환이다. 성공 경로의 실제 별도 claim 호출은0이어야 한다. 준비 합계·전달률·최종p95·drain·두 큐 추이를 비교하며 Lua0누락/필드 대응/단계 호출 수/정합성을 통과해야 성능 수치를 채택한다. 준비·전달만 개선되면 Relay 개선으로만 해석하고 Kafka lag 증가/최종 지연 정체 여부를 구분한다. 기본 서비스 적용은 이번 범위 밖이다.

### Lua 후보 고정 Consumer 계측 계획 — 2026-10-14
