# 최대 10건·10ms Consumer 비교

## 확정 규칙

- 최대10건. 첫 레코드를 poll로 받은 시각부터10ms까지 수집하고 잔여 요청도 처리한다. 타이머는 단조 시계이며 OS/Kafka poll 스케줄링 초과는 별도로 관측한다.
- 수집과 Redis 승인 조회/검증을 마친 뒤 DB 트랜잭션을 시작한다. 수집 중 DB 트랜잭션을 열지 않는다.
- 묶음 전체 DB 롤백. 실패 시 Consumer를 중지하고 해당 offset을 커밋하지 않는다. 재시작 시 같은 그룹에서 재전달한다.
- DB 트랜잭션 커밋·정리 반환 뒤 해당 묶음의 마지막 offset+1을 commitSync한다. DB 커밋 후 offset 전 종료에도 발급 결과가 유지돼야 한다.

## 서비스 반영 (2026-10-15)

- `src/main/.../issuerequest/consumer/CouponBatchConsumer.java`: 수동 poll, 최대10건·첫 수신 후10ms, Redis 검증 후 외부 트랜잭션에서 기존 `processReserved()` 호출. 커밋·정리 반환 후 마지막 offset+1을 동기 커밋한다.
- `CouponIssueConsumer.validateReservation()`을 단건/묶음에서 공유한다. `COUPON_BATCH_ENABLED` 기본false이며 true일 때 단건 Listener 자동 실행을 막는다. `spring.kafka.listener.auto-startup=false`는 양쪽 모두에 적용한다.
- 묶음 오류나 수집 중 파티션 소유권 변경은 작업자를 중지한다. offset 커밋 오류는 브로커 반영 여부가 불명확할 수 있다. 자동 재시도하지 않으며 원인 제거 후 **같은 그룹으로 앱 재시작**한다. 실패 시 API 접수는 계속될 수 있으므로 오류 로그·작업자 중단·적체를 함께 확인해야 한다.
- SmartLifecycle 종료는 wakeup으로 poll을 깨우고 Kafka 자원 종료 뒤 콜백을 호출한다. DB 커밋 후 offset 전 종료는 재전달될 수 있어 기존 requestId 멱등성이 필요하다.
- 실시간10ms 상한 보장은 아니다. 첫 poll 대기와 DB 실행 시간은 수집10ms 밖이고, 스케줄링 초과도 가능하다.
- 실제 서비스 묶음 장애3개, 예약 DB 통합19개, 기존 단건 장애4개, 묶음 단위8개를 각각 실행하여 총34개 통과했다. 전체 프로젝트 테스트 통과와는 구분한다. 최초 Mockito fixture 오류1개는 수정 후 재검증했고 원문을 보존했다.
- 서비스 반영 검증 자료: [RESULTS](../../선착순_쿠폰발급_부하테스트/results/2026-10-15-production-batch/RESULTS.txt). 실제 앱과 과거 테스트 후보의 성능 결과는 아래 서로 다른 절에 구분한다.

## 서비스 전체 부하 재측정 계획 (2026-10-15)

- 가설: 실제 묶음 Consumer가 기존 서비스 단건 경로보다 폭주 후 최종 발급 대기를 줄이는지 확인한다. Relay가 제한하면 Kafka 적체만 줄고 전체 지연은 비슷할 수 있다.
- 순서: 서비스 단건 → 서비스 묶음 → 서비스 묶음 → 서비스 단건. `CouponSystemApplication`으로 실행하고 테스트 후보/Lua/내부 상세 계측은 사용하지 않는다.
- 고정: 기존 서비스 Relay, AOF always, 단일 파티션·Consumer, 풀10, MySQL1CPU/1GiB·Redis0.5CPU/256MiB·Kafka1CPU/1GiB, 호스트 앱 JVM. 전용 인프라·그룹, 실행별 새 JVM/쿠폰. 공유 호스트 및 캐시 편차는 남는다.
- 부하: 재고100000, 고유 사용자/requestId, 100/s20초→1200/s10초→100/s30초, 제한5초·재시도0. 전송 시각별 구간 분류 및 예정/전송/미전송 분리.
- 관측: 예약 HTTP p50/p95/p99, 요청→DB 결과 관측 p50/p95/p99, 마지막 전송 후 전량 완료/두 큐 해소, pending/processing/lag, DB 연결·행 락 대기, CPU·쓰기 지표. DB 조회 목표250ms와 실제 간격·누락을 기록한다.
- 판정: 승인 ID별 결과·이력·재고·수량 일치 및 미완료/중복 없음이 선행 조건. 두 묶음 실행의 최종 p95/전량 완료시간이 단건보다 일관되게 낮으면 이번 조건의 전체 개선 근거로 삼는다. 건별 DB/offset 비용이나 순수 커밋 효과는 이번 외부 관측으로 분리하지 않는다.
- 원시 자료: `results/2026-10-15-production-batch-load/`. 기존 개발 앱/컨테이너 유지, 시험이 만든 자원만 종료한다.

## 과거 테스트 후보: 실험 설계

테스트 전용 수동 Kafka poll 후보를 1건/최대10건 모두에 동일 적용한다. 두 후보의 max.poll.records=10, Kafka 설정·동시성1·Lua Relay 계측ON·AOF always·자원을 고정하고 트랜잭션 크기와 그에 따른 수집 대기/offset 단위만 달라진다. 기본 Spring RECORD Consumer는 auto-startup=false로 두어 경쟁을 막는다. **이 1건 기준은 기존 Spring Listener 자체가 아니므로 프레임워크 차이가 포함된 과거 수치와 직접 개선 배율을 계산하지 않는다.** 해당 비교 당시에는 서비스 코드를 변경하지 않았다.

장애검증 후 1→10→10→1, 재고100000, 100/s20초→1200/s10초→100/s30초, timeout5초/자동재시도0을 재사용한다. 첫20초 저부하와 폭주/회복 요청을 실제 전송 시각으로 구분한다. 기존250ms DB 관측 결과와 함께 monotonic DB 프록시 커밋 반환 시각을 JVM wall anchor에 매핑해 10ms 수준의 대기를 확인한다. 이는 실제 commit 직후 정리까지 포함하는 상한이며 순수 서버 commit timestamp가 아니다. HTTP 시작 이전 Kafka 대기만을 분리한 값도 아니다.

수집 대기, 묶음 크기 분포, DB/offset 시간과 횟수, 요청→커밋 반환·외부 관측 p95/p99, pending/lag, 전량 해소와 ID/수량 정합성을 기록한다. poll은 수집 이후 DB 밖에서만 실행되는지 검증한다. 상세 로그는 장애시험에서만 켜고 부하는 메모리에 수집해 종료 시 출력한다.

### 저부하와 대기 비용

묶음 수집 자체의 저부하 p95는10.691/10.729ms다. 단건은 약0.002ms였다. Kafka poll수신→DB반환 p95도 단건30.873/24.562ms, 묶음36.280/47.246ms로 늘었다. 수집뿐 아니라 묶음 내 작업 완료까지 기다리는 효과가 포함된다. 10ms는 논리 deadline이고 관측된 수집 최대는11.007/11.306ms로 OS/클라이언트 스케줄링 초과가 있었다. 엄격한 실시간10ms 상한을 보장한 결과는 아니다.

### 정합성과 실패 경계

- Kafka에 쌓인13건을10+3으로 처리하고, 이후 단독1건도 추가 요청 없이 처리했다. 수집 중 트랜잭션 없음 확인.
- 다섯 번째 INSERT 오류에서10건 전체 롤백·offset유지. 재시작 후 같은 실패10건과 후속3건 완료.
- DB10건 커밋 후 offset 전 강제종료. 같은 offset/요청ID 묶음 재전달 시 기존 결과ID·발급ID와 수량 유지.
- 부하4회에서 요청ID 집합·사용자·쿠폰·이력·결과·재고·수량 및 연속offset/묶음size/시간경계 검증. lag0만으로 판정하지 않음.

최초 장애시험은1통과/2실패였다. 오류주입 CHECK가 다른 쿠폰의 기존 사용자에도 걸린 fixture 문제와, 강제종료 후 session timeout보다 짧은 관찰시간 문제였다. CHECK를 해당쿠폰에 한정하고 테스트 관찰을90초로 늘려3개 통과했다. Kafka session timeout이나 서비스 로직은 변경하지 않았으며 최초 실패 원문도 보존했다.

### 범위와 남은 작업

모든 부하에서 Relay 및 묶음 계측은 켜져 있다. 무계측 성능 주장이 아니며 공유 호스트·디스크·캐시/실행 순서 편차가 남는다. 트랜잭션 크기뿐 아니라 수집·offset 단위와 JPA 조회 재사용/flush 비용도 달라져 순수 DB 커밋만의 효과는 아니다.

첫 후보와 서비스 묶음 옵션은 단일 파티션·단일 Consumer에 한정한다. 위 성능 실험 당시에는 서비스 적용하지 않았다. 마지막 단건 실행은 최종 스냅샷 후 앱 종료 중 Relay의 Redis 자원 접근 오류가 다시 발생했다. 별도 종료 순서 수정 과제로 유지한다. 시험 앱/컨테이너만 정리했고 기존 개발 MySQL/Redis는 유지했다.
